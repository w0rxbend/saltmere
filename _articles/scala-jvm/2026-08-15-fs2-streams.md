**Gist.** Streaming pipelines fail in three recurring ways: a resource leaks when the consumer dies mid-traversal, a fast producer exhausts memory ahead of a slow consumer, and a running loop cannot be interrupted. **fs2** — the 3.x line, built on **Cats Effect 3** and cross-published for Scala 3 — addresses all three by describing the pipeline as an immutable value that is interpreted only at a **compile** boundary, with pull-based demand and lexically scoped finalizers. The cost is that every stage is a reified program rather than a loop: element-at-a-time interpretation is expensive, so fs2 moves data in batches, and the batching is visible in performance whenever it degrades.

## A stream is a program, not a collection

`Stream[F, O]` describes a process that may evaluate effects in an effect type `F` and emit zero or more values of type `O`. Construction performs no work: `Stream.eval(IO.println("hi")).repeat.take(3)` allocates no threads and opens no sockets. Interpretation begins at `compile`:

```scala
val program: IO[Vector[Int]] =
  Stream.range(0, 100).covary[IO].compile.toVector
```

`compile.drain`, `compile.toList` and `compile.lastOrError` each fold the stream into a single `F` value to be submitted to the runtime, in the same way as the `IO` values in [Cats Effect 3: fibers and resources](/articles/scala-jvm/2026-08-13-cats-effect-3-fibers-resources).

The interpreter is **pull-based**: the downstream requests the next batch, and upstream stages run only to satisfy that request. **No stage runs ahead of demand, so there is no unbounded buffer to fill** — backpressure is a consequence of the evaluation order rather than a policy layered on top. Decoupling is opt-in and the bound is written in the code: `buffer(64)`, `prefetchN(4)`, or a `Channel.bounded`.

## Chunks and the cost of interpretation

A pull per element would pay interpreter dispatch and allocation on every element. fs2 streams therefore emit **`Chunk[O]`**: an immutable, array-backed batch with `O(1)` indexing. `Files[IO].readAll` takes an explicit chunk size, and the single-argument overload defaults it to 64 KiB. Operators such as `map` and `filter` fuse over a chunk internally, so per-element overhead is amortised across the chunk.

Two consequences follow. First, **throughput tracks chunk size**. A pipeline fed one-element chunks — readily produced by `Stream.eval` in a loop, or by a queue configured to dequeue singly — pays that overhead once per element instead of once per batch. No published benchmark in the cited sources quantifies the gap, but it is proportional to the chunk size the source emits, and it is a property of the source rather than of the work being done. The observable is the chunk-size distribution itself: `.chunks.map(_.size)` reports the sizes the source emits, and `chunkN(4096)` or `groupWithin(4096, 100.millis)` repacks it. Second, when per-element work is trivial, moving the work to the chunk level — `mapChunks(c => c.map(f))`, or `chunkN(n).map(processBatch)` — replaces n effect evaluations with one.

## Resource scoping

`Stream.bracket(acquire)(release)` binds a resource to the lifetime of the stream; `Stream.resource(r)` lifts an existing `Resource[F, A]`. The guarantee is that **release runs on every exit path: normal completion, a raised error, and interruption** — including interruption originating in a concurrent combinator such as `timeout` or `interruptWhen`, and cancellation of the enclosing fiber by the runtime.

Scopes nest. A resource acquired inside a `flatMap` is released when the inner stream ends, not when the outer pipeline terminates. This is the invariant that makes `Files[IO].readAll(path).take(10)` safe: **the downstream stops pulling, the enclosing scope closes, and the file handle is released at that point** rather than at end of input.

## Concurrency operators and what each preserves

fs2 concurrency is built on Cats Effect fibers and is cancellation-safe.

| Operator | Ordering | Behaviour | Applicable when |
|----------|----------|--------------|-------------------|
| `parEvalMap(n)(f)` | preserved | ≤ n effects in flight, results emitted in input order | per-element I/O where order matters |
| `parEvalMapUnordered(n)(f)` | not preserved | ≤ n in flight, emitted as completed | writes, fire-and-forget enrichment |
| `s1.merge(s2)` | interleaved | both run, emit whichever is ready | combining independent sources |
| `s1.concurrently(s2)` | s1 only | s2 runs in background and is terminated when s1 ends | heartbeats, metrics flushers |
| `broadcastThrough(p1, p2)` | per-pipe | every element is fanned out to several pipes | one source, many sinks |

The load-bearing property is that **`parEvalMap` still backpressures**: if the downstream stops pulling, at most `n` effects complete and the upstream then stalls. Concurrency raises the in-flight bound from 1 to n; it does not remove the bound. `broadcastThrough` proceeds at the pace of the **slowest** pipe, so a lagging sink throttles every sink; a `prefetchN` in front of the sink permitted to lag decouples it up to that bound.

### Implementation sketch (Scala)

Read a growing file, decode, batch for write efficiency, and write with bounded parallelism, using the fs2-io **Files API**:

```scala
import cats.effect.{IO, IOApp}
import fs2.io.file.{Files, Path}
import scala.concurrent.duration.*

object IngestLog extends IOApp.Simple:

  def writeBatch(lines: List[String]): IO[Unit] =
    IO.println(s"wrote ${lines.size} records") // stands in for a DB or HTTP call

  val run: IO[Unit] =
    Files[IO]
      .tail(Path("/var/log/app/events.ndjson"), pollDelay = 250.millis)
      .through(fs2.text.utf8.decode)
      .through(fs2.text.lines)
      .filter(_.nonEmpty)
      .groupWithin(500, 1.second)          // emits at 500 elements, or at 1 s with whatever accumulated
      .map(_.toList)
      .parEvalMapUnordered(8)(writeBatch)  // ≤ 8 batch writes in flight
      .compile
      .drain
```

Three properties hold without additional code. The file handle is released on cancellation, because `tail` acquires it inside a scope the compiled program owns. `groupWithin` bounds **both** batch size and flush latency, so a quiet source does not hold records indefinitely. And when `writeBatch` slows, demand stops propagating upstream, so the tail continues polling without accumulating an unbounded buffer. Substituting `Stream.fromQueueUnterminated(queue)` for the source leaves every downstream stage unchanged. The network side of fs2-io carries the same scoping: `Network[IO].client(...)` returns a `Resource[IO, Socket[IO]]` with the same lifecycle guarantees.

A direct-style alternative with comparable scoping guarantees is [Ox's structured concurrency on Scala 3](/articles/scala-jvm/2026-08-03-ox-structured-concurrency-scala3), which derives them from virtual threads and lexical scopes rather than from a reified program. The compositional consequence of fs2's representation is that a `Pipe[F, A, B]` is exactly `Stream[F, A] => Stream[F, B]`, so a pipeline factors into named, independently testable functions.

## Pitfalls

- **A pipeline built without `compile` runs nothing.** The value is discarded and no effect is evaluated; the symptom is silence rather than an error, because construction is total.
- **Single-element chunks move interpretation overhead from per-batch to per-element.** A source emitting one element per chunk defeats the amortisation that `map` and `filter` obtain by fusing over a chunk. `.chunks.map(_.size)` distinguishes this from a slow effect.
- **`broadcastThrough` runs at the slowest pipe's pace.** One lagging sink stalls the shared upstream, so every other sink starves even though its own work is fast.
- **`parEvalMapUnordered` reorders output.** Downstream logic that assumes input order — sequence numbers, last-write-wins, ordered file writes — is silently wrong rather than failing.
- **Raising `n` in `parEvalMap` raises peak resource usage, not throughput, when the downstream is the bottleneck.** Up to `n` results are held completed and unconsumed while the upstream stalls.
- **A resource acquired in an inner `flatMap` is released when the inner stream ends.** Code that expects the handle to remain open for the rest of the outer pipeline observes a use-after-close.
