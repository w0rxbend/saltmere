Every streaming bug you've ever shipped is one of three things: a file handle that leaked when the consumer crashed halfway through, a fast producer that OOM-killed a slow consumer, or a `while` loop that couldn't be interrupted. **fs2** (currently **3.13.0**, built on **Cats Effect 3.7.0**, cross-published for Scala 3 and — since this release — a genuinely multi-threaded Scala Native 0.5) is designed so that all three are unrepresentable. A stream that terminates, fails, or gets cancelled runs its finalizers. A slow consumer slows the producer. And it's all just a value until you say otherwise.

## A stream is a program, not a collection

`Stream[F, O]` is a description of a process that may evaluate effects in `F` and emit zero or more values of type `O`. Nothing happens when you build one — `Stream.eval(IO.println("hi")).repeat.take(3)` allocates no threads, opens no sockets. Evaluation begins only at the **compile** boundary:

```scala
val program: IO[Vector[Int]] =
  Stream.range(0, 100).covary[IO].compile.toVector
```

`compile.drain`, `compile.toList`, `compile.lastOrError` — each folds the stream into a single `F` value you hand to your runtime, exactly like the `IO`s in [Cats Effect 3: fibers and resources](/articles/scala-jvm/2026-08-13-cats-effect-3-fibers-resources). Because a stream is **pull-based**, the compiled program works by the downstream *asking* for the next batch. Nothing upstream runs ahead of demand, which is why fs2 people say **backpressure by construction**: there is no unbounded buffer to fill because there is no push. Where you *want* decoupling, you opt in with an explicit bound — `buffer(64)`, `prefetchN(4)`, or a `Channel.bounded` — and the bound is visible in the code.

## Chunks are why it's fast

A naive pull-per-element design would drown in allocation and virtual dispatch. fs2 streams don't emit elements; they emit **`Chunk[O]`** — an immutable, array-backed, `O(1)`-indexed batch. `Files[IO].readAll` emits 64 KiB chunks; a Kafka consumer emits one chunk per poll. Operators like `map` and `filter` fuse over chunks internally, so the per-element overhead amortizes across the chunk.

This has two practical consequences. First, **throughput tracks chunk size**: a pipeline fed one-element chunks (easy to cause with `Stream.eval` in a loop, or a badly configured queue) can be 10–50x slower than the same pipeline fed 4096-element chunks, purely from interpreter overhead. Check with `.chunks.map(_.size)` when a pipeline is mysteriously slow, and repack with `chunkN(4096)` or `groupWithin(4096, 100.millis)`. Second, when the per-element work is trivial, drop to the chunk level yourself: `mapChunks(c => c.map(f))` or `chunkN(n).map(processBatch)` turns n effect evaluations into one.

## Resources that survive every exit path

fs2 predates Cats Effect's `Resource` and integrates with it completely. `Stream.bracket(acquire)(release)` scopes a resource to the stream's lifetime; `Stream.resource(r)` lifts an existing `Resource[F, A]`. The guarantee is the one that matters in production: the release action runs whether the stream **completes, raises, or is interrupted** — including interruption from a concurrent combinator like `timeout` or `interruptWhen`, or a fiber cancellation from the runtime. Scopes nest, so a resource acquired inside a `flatMap` is released when that inner stream ends, not when the whole pipeline does. This is the property that makes `Files[IO].readAll(path)` safe to `take(10)` from: the file handle closes as soon as the downstream stops pulling.

## Concurrency operators, and what each preserves

All fs2 concurrency is built on Cats Effect fibers and is cancellation-safe. The ones you'll actually use:

| Operator | Ordering | What it does | Reach for it when |
|----------|----------|--------------|-------------------|
| `parEvalMap(n)(f)` | preserved | ≤ n effects in flight, results emitted in input order | per-element I/O where order matters |
| `parEvalMapUnordered(n)(f)` | not preserved | ≤ n in flight, emit as completed | writes, fire-and-forget enrichment |
| `s1.merge(s2)` | interleaved | run both, emit whichever is ready | combining independent sources |
| `s1.concurrently(s2)` | s1 only | run s2 in background, kill it when s1 ends | heartbeats, metrics flushers |
| `broadcastThrough(p1, p2)` | per-pipe | fan out every element to several pipes | one source, many sinks |

The detail worth internalizing: `parEvalMap` still backpressures. If the downstream stops pulling, at most `n` effects finish and then the upstream stalls — concurrency raises the in-flight bound from 1 to n, it doesn't remove it. And `broadcastThrough` runs at the pace of the *slowest* pipe, so a laggy sink slows every sink; put a `prefetchN` in front of the one that's allowed to lag.

## A real pipeline: tail, batch, write concurrently

The canonical shape — read a growing file (or a queue), parse, batch for efficiency, write with bounded parallelism — in the fs2-io **Files API**:

```scala
import cats.effect.{IO, IOApp}
import fs2.Stream
import fs2.io.file.{Files, Path}
import scala.concurrent.duration.*

object IngestLog extends IOApp.Simple:

  def writeBatch(lines: List[String]): IO[Unit] =
    IO.println(s"wrote ${lines.size} records") // real code: DB/HTTP call

  val run: IO[Unit] =
    Files[IO]
      .tail(Path("/var/log/app/events.ndjson"), pollDelay = 250.millis)
      .through(fs2.text.utf8.decode)
      .through(fs2.text.lines)
      .filter(_.nonEmpty)
      .groupWithin(500, 1.second)          // Chunk of ≤500, flushed every 1s
      .map(_.toList)
      .parEvalMapUnordered(8)(writeBatch)  // ≤8 batch-writes in flight
      .compile
      .drain
```

Every safety property discussed above is present without extra code: the file handle closes on cancellation, `groupWithin` bounds both batch size and latency, and if `writeBatch` slows down, the tail simply polls without buffering unboundedly. Swap the source for `Stream.fromQueueUnterminated(queue)` and nothing downstream changes. For network work, the same release also unified the TCP/UDP/Unix-socket APIs and added `Socket#sendFile` — `Network[IO].client(...)` hands you a `Resource[IO, Socket[IO]]` with identical lifecycle guarantees.

If this style appeals but the effect wrapper doesn't, the direct-style alternative is [Ox's structured concurrency on Scala 3](/articles/scala-jvm/2026-08-03-ox-structured-concurrency-scala3) — Ox gets similar scoping guarantees from virtual threads and lexical scopes rather than from a reified program. fs2's edge is composition: a `Pipe[F, A, B]` is just `Stream[F, A] => Stream[F, B]`, so pipelines factor into named, testable, reusable pieces.

**Try next:** take any loop in your codebase that reads-transforms-writes, port it to the tail/batch/write skeleton above, then deliberately kill it mid-run with `IO.sleep(3.seconds) *> fiber.cancel` — verify with `lsof` that the file handle is gone, then check `.chunks.map(_.size).evalTap(IO.println)` to see what chunk sizes your source actually produces.
