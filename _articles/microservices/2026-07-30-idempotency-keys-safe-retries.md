A retry is a bet that the first attempt didn't happen. Sometimes you lose that bet. The request reached the server, the charge went through, the row was inserted — and then the response died in the network on the way back. Your timeout fired, your retry logic woke up (or your circuit breaker half-opened and let one probe through — both covered in earlier articles here), and you sent the same `POST /charges` again. Now the customer has been billed twice.

This is not a bug you can retry your way out of. Once you accept **at-least-once** delivery — and any system with timeouts and retries has accepted it — duplicate *delivery* is guaranteed for some fraction of requests. The only open question is whether duplicate delivery causes duplicate *side effects*. Newman makes the point directly in *Building Microservices* (2nd ed.): safe retries require the operation to be idempotent, and for operations that aren't naturally idempotent you have to *make* them so.

`GET`, `PUT`, and `DELETE` can be idempotent by construction. `POST "create a charge"` is the hard case: its whole purpose is a side effect, and running it twice means two charges. You can't reshape the semantics, so instead you give the server a way to recognize a repeat.

## The key

The client generates a unique value per logical operation and sends it on every attempt of that operation:

```
POST /charges
Idempotency-Key: 8f14e45f-ea0d-4f2a-9b3c-1c2d3e4f5a6b
```

The IETF draft "The Idempotency-Key HTTP Header Field" defines this precisely: the header carries "a unique value generated by the client which the resource uses to recognize subsequent retries." The key identifies the *intent*, not the HTTP request — the first attempt and its three retries all carry the same key. Stripe recommends a V4 UUID or a random string with enough entropy, up to 255 characters.

The contract the server offers in return has three cases:

1. **First time I've seen this key** — do the work, save the outcome, return it.
2. **I've seen this key and I'm done** — return the *saved* response, don't re-run the work. The draft: "The resource SHOULD respond with the result of the previously completed operation, success or an error."
3. **I've seen this key and I'm still working on it** — a concurrent retry raced the original. Reject the second one; don't run it in parallel. The draft says respond with HTTP `409` conflict.

Case 3 is the one people get wrong. It is not enough to check "have I seen this key" at the top of the handler — two requests can both pass that check before either has written anything. The dedupe has to be atomic.

## The server-side recipe

Make the database settle the race. Put a **unique constraint on the key** and let exactly one `INSERT` win.

```sql
CREATE TABLE idempotency_keys (
    idempotency_key   TEXT        NOT NULL,
    request_fingerprint TEXT      NOT NULL,   -- hash of method+path+body
    status            TEXT        NOT NULL,   -- 'in_flight' | 'completed'
    response_code     INT,                    -- filled in when completed
    response_body     JSONB,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (idempotency_key)
);
```

The handler's flow: try to claim the key with an `INSERT`, marking it `in_flight`. If the insert succeeds, *you* own this operation — do the work, then update the row to `completed` with the saved response. If the insert hits the unique constraint, someone else got there first, so read their row and either replay their answer or reject the still-in-flight duplicate.

```python
@app.post("/charges")
def create_charge():
    key = request.headers["Idempotency-Key"]
    fingerprint = sha256(request.method, request.path, request.get_data())

    # Atomic claim: only the first request for this key inserts a row.
    row = db.execute("""
        INSERT INTO idempotency_keys (idempotency_key, request_fingerprint, status)
        VALUES (%s, %s, 'in_flight')
        ON CONFLICT (idempotency_key) DO NOTHING
        RETURNING idempotency_key
    """, (key, fingerprint))

    if row is None:                       # conflict: key already exists
        prior = db.execute("SELECT * FROM idempotency_keys WHERE idempotency_key = %s", (key,))
        if prior["request_fingerprint"] != fingerprint:
            abort(422, "Idempotency-Key reused with a different request body")
        if prior["status"] == "in_flight":
            abort(409, "A request with this Idempotency-Key is still being processed")
        return jsonify(prior["response_body"]), prior["response_code"]   # replay

    # We won the insert -> we run the side effect exactly once.
    result, code = do_the_charge(request.json)
    db.execute("""
        UPDATE idempotency_keys
        SET status = 'completed', response_code = %s, response_body = %s
        WHERE idempotency_key = %s
    """, (code, json.dumps(result), key))
    return jsonify(result), code
```

`ON CONFLICT ... DO NOTHING` plus a `RETURNING` that comes back empty is the whole concurrency primitive: the database guarantees exactly one inserter, so exactly one caller runs `do_the_charge`. Brandur's Postgres write-up reaches the same place from the other direction — a unique constraint on the key and a `locked_at` / recovery-point column, wrapped in a `SERIALIZABLE` transaction so "if two different transactions both try to lock any one key, one of them will be aborted by Postgres."

Two details in that snippet are load-bearing:

**The fingerprint.** Store a hash of the request and compare it on replay. If the same key arrives with a *different* body, that's a client bug — a reused key, not a retry — and you must refuse rather than silently return the wrong operation's result. Stripe: "The idempotency layer compares incoming parameters to those of the original request and errors if they're not the same." The draft makes it a `MUST`: the key "MUST NOT be reused with another request with a different request payload," answered with `422`.

**The commit boundary.** The `do_the_charge` side effect and the `UPDATE ... 'completed'` must land in the *same* transaction as the work they describe, or the saved response can disagree with reality after a crash between them. This is why Stripe notes it saves "results only after the execution of an endpoint begins" and lets you retry anything that failed validation or lost the concurrent race — those never produced a saved outcome.

## TTL: keys don't live forever

The table grows without bound unless you reap it. Set a retention window and delete old keys:

```sql
DELETE FROM idempotency_keys WHERE created_at < now() - INTERVAL '72 hours';
```

Pick the window from how long a retry could plausibly arrive, not from convenience. Stripe keeps keys for at least 24 hours ("You can remove keys from the system automatically after they're at least 24 hours old"); Brandur reaps at around 72 hours to leave room for post-deploy recovery. The draft leaves the number to you but insists you publish it: the resource "SHOULD define such expiration policy and publish it in the documentation." The risk is asymmetric — reap too early and a late retry re-runs a side effect that already happened, which is exactly the duplicate you built this table to prevent.

| Case | Signal | Server action |
|---|---|---|
| New key | insert succeeds | run once, save response |
| Completed key, same body | conflict, `status=completed` | replay saved response |
| In-flight key | conflict, `status=in_flight` | `409`, tell client to retry later |
| Reused key, different body | conflict, fingerprint mismatch | `422`, reject |
| Key past TTL | no row (reaped) | treated as new — accepted risk |

## Where the responsibility sits

Idempotency keys don't replace retries, timeouts, or circuit breakers — they're the thing that makes those safe to point at a non-idempotent endpoint. The client still owns generating a stable key per operation and retrying with backoff and jitter; the server owns the atomic claim, the fingerprint check, and the TTL. Get the unique constraint right and the concurrent case — the one that actually bites in production — is handled by the database, not by hope.

**Try next:** Take the handler above and hammer one key with two concurrent requests (e.g. `curl` twice in parallel with the same `Idempotency-Key`); confirm exactly one runs `do_the_charge` and the other gets a `409`, then remove the `ON CONFLICT` clause and watch both slip through — that gap is the double charge.
