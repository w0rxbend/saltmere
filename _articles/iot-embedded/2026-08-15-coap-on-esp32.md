Every MQTT node I ship carries two costs that never show up in the demo: a broker somewhere that has to stay alive, and a TCP connection the node has to hold open — or pay a full handshake to re-establish every time it wakes. For a mains-powered gateway that is fine. For a coin-cell air-quality node that wakes once a minute, samples PM2.5, and wants to be asleep again in 200 ms, it is mostly overhead. **CoAP** — the Constrained Application Protocol, **RFC 7252** — was designed for exactly that node: it is REST semantics over UDP, small enough that a request and its response can each fit in a single datagram, with no broker in the path.

## The model: REST, but over UDP

If you know HTTP you already know CoAP. It has the same four methods — **GET, PUT, POST, DELETE** — acting on URI-addressed resources like `coap://node.local/sensor/pm25`, and response codes that mirror HTTP (`2.05 Content`, `4.04 Not Found`). The difference is everything underneath. There is no connection and no broker: a client sends a request datagram straight to the node, the node answers with a datagram. Because reliability can't come from TCP, CoAP builds a thin layer of its own on top of UDP with two message types:

- **Confirmable (CON)** messages must be acknowledged; if the ACK doesn't arrive, the sender retransmits with exponential backoff. This is your at-least-once delivery.
- **Non-confirmable (NON)** messages are fire-and-forget — one datagram, no ACK, no retransmit. Perfect for a stream of readings where the next sample is along in a second anyway and you'd rather not spend radio time on ACKs.

You pick per message. That granularity is the point: a firmware-critical PUT goes CON, a routine telemetry NON goes out and the radio goes back to sleep.

Two extensions matter for sensors. **Observe (RFC 7641)** bolts a publish/subscribe feel onto the request/response core: a client sends a GET with an `Observe` option, and the node keeps sending updated representations whenever the value changes — push, without a broker in the middle. And **block-wise transfer (RFC 7959)** lets you move a payload larger than one datagram (a firmware chunk, a buffered CSV) in numbered blocks, so you never rely on IP fragmentation, which constrained networks handle badly. Security is **DTLS** — TLS's datagram cousin — most commonly with a pre-shared key (`coaps://`, UDP 5684) on nodes too small for certificates.

## When CoAP wins, and when it doesn't

| | CoAP | MQTT |
|---|---|---|
| Transport | UDP (datagram) | TCP (connection) |
| Broker required | No — direct to node | Yes |
| Model | Request/response + Observe | Publish/subscribe |
| Multicast discovery | Yes (`.well-known/core`) | No |
| Wake-sample-sleep cost | One datagram | Reconnect or keepalive |
| Security | DTLS | TLS |

CoAP wins when nodes are the *servers* — you query them, or observe them — and you want no broker to operate, no held-open socket, and the ability to **multicast-discover** every node on a segment by GETting `/.well-known/core`. It loses when you have many-to-many fan-out, offline subscribers who must get buffered messages, or a cloud backend that already speaks MQTT and expects a broker to decouple producers from consumers. CoAP has no retained messages and no queue; if nobody's listening when a NON goes out, it's gone. My honest rule: CoAP for LAN and edge, where a controller polls or observes a fleet of small nodes; MQTT once the data has to cross the internet to a platform built around a broker. They coexist happily — a gateway can observe CoAP nodes locally and republish to MQTT upstream.

## Running it on the ESP32 with ESP-IDF

ESP-IDF wraps **libcoap** (currently the 4.3.x line). As of **ESP-IDF v6.0** the CoAP support is a managed component rather than part of the core tree — you pull it from the ESP Component Registry, the same way esp-mqtt now works:

```
idf.py add-dependency "espressif/coap^4.3.5"
```

The registry also ships ready-made `coap_server` and `coap_client` examples (`idf.py create-project-from-example "espressif/coap:coap_server"`). Here is the core of a server: a resource at `/sensor/pm25` whose GET handler returns a live reading as JSON, marked observable so clients can subscribe.

```c
#include "coap3/coap.h"

/* Your driver — e.g. the SPS30/PMS5003 read from the air-quality nodes. */
extern float read_pm25(void);

/* CoAP GET handler: fill 'response' with a 2.05 Content payload. */
static void hnd_pm25_get(coap_resource_t *resource, coap_session_t *session,
                         const coap_pdu_t *request, const coap_string_t *query,
                         coap_pdu_t *response)
{
    char buf[48];
    int len = snprintf(buf, sizeof(buf), "{\"pm25\":%.1f}", read_pm25());

    coap_pdu_set_code(response, COAP_RESPONSE_CODE_CONTENT);   /* 2.05 */
    coap_add_data_large_response(resource, session, request, response, query,
                                 COAP_MEDIATYPE_APPLICATION_JSON,
                                 -1, 0, len, (const uint8_t *)buf, NULL, NULL);
}

void coap_server_task(void *arg)
{
    coap_context_t *ctx = coap_new_context(NULL);

    coap_address_t addr;
    coap_address_init(&addr);
    addr.addr.sin.sin_family = AF_INET;
    addr.addr.sin.sin_port   = htons(COAP_DEFAULT_PORT);       /* 5683 */
    coap_new_endpoint(ctx, &addr, COAP_PROTO_UDP);

    coap_resource_t *res = coap_resource_init(coap_make_str_const("sensor/pm25"), 0);
    coap_register_handler(res, COAP_REQUEST_GET, hnd_pm25_get);
    coap_resource_set_get_observable(res, 1);                  /* enable Observe */
    coap_add_resource(ctx, res);

    /* Event loop: service sockets, run retransmits and observe notifications. */
    while (1) {
        coap_io_process(ctx, COAP_IO_WAIT);
    }
}
```

From a laptop, `coap-client -m get coap://<node-ip>/sensor/pm25` returns the JSON in one round trip; add `-s 30` and you're using Observe, and the node pushes a fresh reading every time you call `coap_resource_notify_observers(res, NULL)` after a new sample. The caveat to keep in front of you: `coap_add_data_large_response` transparently splits oversized payloads into block-wise transfer, so it's the right call even for small bodies — but it means the buffer you hand it must stay valid until libcoap has sent every block, so build the string into a stack buffer inside the handler as above rather than pointing at something that goes out of scope. And UDP means *you* own reliability: use CON for anything that must land, size your DTLS record buffers against your available heap (the same mbedTLS memory pressure that bites MQTT-over-TLS applies here), and remember Observe notifications are best-effort unless you send them confirmable.

**Try next:** flash the stock `coap_server` example onto a spare devkit, then run `coap-client -m get coap://<ip>/.well-known/core` and watch it enumerate the node's resources — that one multicast-able discovery call is the capability MQTT simply doesn't have.
