**Gist.** A battery sensor node that wakes, samples, and sleeps pays for MQTT twice: a broker that must stay alive somewhere, and a TCP connection that must either be held open or re-handshaked on every wake. The Constrained Application Protocol (CoAP, **RFC 7252**) removes both by putting Representational State Transfer (REST) semantics directly on User Datagram Protocol (UDP) datagrams, so a request and its response can each fit in one packet with no intermediary. The cost is that UDP supplies no reliability, so CoAP re-implements a minimal retransmission layer in the application protocol, and everything it does not re-implement — queuing, retained state, offline delivery — is absent.

## The model: REST over UDP

CoAP exposes the same four methods as Hypertext Transfer Protocol (HTTP) — **GET, PUT, POST, DELETE** — over Uniform Resource Identifier (URI) addressed resources such as `coap://node.local/sensor/pm25`, with response codes that mirror HTTP's classes (`2.05 Content`, `4.04 Not Found`). Everything below the method differs. There is no connection and no broker: a client sends a request datagram to the node, the node answers with a datagram. The default port is **5683** for plaintext CoAP and **5684** for CoAP over Datagram Transport Layer Security (DTLS).

Because reliability cannot come from Transmission Control Protocol (TCP), RFC 7252 defines a **message layer** beneath the request/response layer, carrying a 4-byte fixed header with a message type, a **16-bit Message ID** used for deduplication and acknowledgement matching, and a token used to correlate a response with its request even when the response arrives separately from the acknowledgement. Two message types carry the trade-off:

- **Confirmable (CON).** The receiver must return an acknowledgement (ACK) carrying the same Message ID. If none arrives, the sender retransmits with exponential backoff; RFC 7252's defaults are an initial **ACK_TIMEOUT of 2 seconds** and **MAX_RETRANSMIT of 4**, after which the exchange is abandoned. This yields at-least-once delivery — the deduplication window over Message IDs is what keeps a retransmitted request from being executed twice.
- **Non-confirmable (NON).** One datagram, no ACK, no retransmission. Loss is silent.

The choice is **per message**, not per connection: a configuration PUT can be CON while routine telemetry goes NON and the radio returns to sleep without waiting for a round trip.

A response may be returned **piggybacked** inside the ACK when the value is available immediately, or, if the server needs longer than its ACK deadline, as an empty ACK followed later by a **separate response** matched by token. A node that cannot answer within the acknowledgement window therefore does not force the client into a retransmit storm.

## Observe and block-wise transfer

**Observe (RFC 7641)** adds push to a protocol that has only request/response. A client issues a GET carrying the `Observe` option; the server registers the client and thereafter sends further responses, sharing the original request's token, whenever the resource representation changes. Each notification carries an **Observe option value that acts as a sequence number**, so a client receiving notifications out of order over UDP can discard a stale one rather than regress. The registration is soft state: the server may drop it at any time, and **notifications sent as NON are best-effort** — only confirmable notifications give the server a signal (a missing ACK, or a reset) that the observer is gone.

**Block-wise transfer (RFC 7959)** moves a payload larger than one datagram as a sequence of numbered blocks negotiated between peers, with block sizes drawn from the powers of two from **16 to 1024 bytes**. The transfer is driven by the client requesting successive block numbers, which keeps a constrained server from having to buffer an entire body, and avoids relying on Internet Protocol (IP) fragmentation.

Security is **DTLS**, most often with a pre-shared key on nodes without room for certificate chains, addressed as `coaps://`.

## When CoAP applies

| | CoAP | MQTT |
|---|---|---|
| Transport | UDP (datagram) | TCP (connection) |
| Broker required | No — direct to node | Yes |
| Model | Request/response + Observe | Publish/subscribe |
| Multicast discovery | Yes (`.well-known/core`) | No |
| Wake-sample-sleep cost | One datagram | Reconnect or keepalive |
| Security | DTLS | TLS |

CoAP fits when the nodes are the *servers* — queried or observed by a controller — and no broker is wanted in the path. Its discovery mechanism is a GET on `/.well-known/core`, which can be sent to a multicast address to enumerate the resources of every node on a segment; MQTT has no equivalent.

It does not fit many-to-many fan-out, subscribers that are offline when a message is produced, or a backend already built around a broker. **CoAP has no retained messages and no queue**: a NON emitted with no listener is lost, and an Observe registration exists only while the server chooses to keep it. The two compose in the obvious way — a gateway observes CoAP nodes on the local network and republishes upstream over MQTT.

## Running it on the ESP32 with ESP-IDF

ESP-IDF's CoAP support is a wrapper around **libcoap**. It is not part of the core tree: it ships as the managed component `espressif/coap`, maintained in `espressif/idf-extra-components` and retrieved from the ESP Component Registry:

```
idf.py add-dependency "espressif/coap"
```

The registry also ships `coap_server` and `coap_client` examples (`idf.py create-project-from-example "espressif/coap:coap_server"`). The core of a server is a resource at `/sensor/pm25` whose GET handler returns a live reading as JavaScript Object Notation (JSON), marked observable.

```c
#include "coap3/coap.h"

/* Sensor driver — e.g. the SPS30/PMS5003 used on the air-quality nodes. */
extern float read_pm25(void);

/* CoAP GET handler: fill 'response' with a 2.05 Content payload. */
static void hnd_pm25_get(coap_resource_t *resource, coap_session_t *session,
                         const coap_pdu_t *request, const coap_string_t *query,
                         coap_pdu_t *response)
{
    char buf[48];
    int len = snprintf(buf, sizeof(buf), "{\"pm25\":%.1f}", read_pm25());

    coap_pdu_set_code(response, COAP_RESPONSE_CODE_CONTENT);   /* 2.05 */
    /* Hands the body to libcoap, which splits it block-wise if it exceeds one block. */
    coap_add_data_large_response(resource, session, request, response, query,
                                 COAP_MEDIATYPE_APPLICATION_JSON,
                                 -1, 0, len, (const uint8_t *)buf, NULL, NULL);
}

void coap_server_task(void *arg)
{
    coap_context_t *ctx = coap_new_context(NULL);

    coap_address_t addr;
    coap_address_init(&addr);
    addr.addr.sin.sin_family = AF_INET;
    addr.addr.sin.sin_port   = htons(COAP_DEFAULT_PORT);       /* 5683 */
    coap_new_endpoint(ctx, &addr, COAP_PROTO_UDP);

    coap_resource_t *res = coap_resource_init(coap_make_str_const("sensor/pm25"), 0);
    coap_register_handler(res, COAP_REQUEST_GET, hnd_pm25_get);
    coap_resource_set_get_observable(res, 1);                  /* enable Observe */
    coap_add_resource(ctx, res);

    /* Event loop: services sockets, drives retransmits and observe notifications. */
    while (1) {
        coap_io_process(ctx, COAP_IO_WAIT);
    }
}
```

`coap_io_process` is the single point where retransmission timers advance and queued notifications leave the node; a handler that blocks — a slow synchronous sensor read, for instance — stalls every other exchange, including confirmable retransmits, because there is one loop. Notifications are emitted by calling `coap_resource_notify_observers(res, NULL)` after a new sample is taken; the loop then delivers one response per registered observer.

From a host, `coap-client -m get coap://<node-ip>/sensor/pm25` returns the JSON in one round trip, and `-s 30` registers an Observe for 30 seconds.

## Pitfalls

- **A payload buffer that goes out of scope truncates or corrupts later blocks.** `coap_add_data_large_response` may split a body across several block-wise transfers sent after the handler returns, so the payload has to remain valid past the return; the final two arguments are a release callback and its application pointer, and a caller-owned buffer handed over that way must stay alive until that callback fires.
- **Observe registrations vanish without notice.** A server that only ever sends NON notifications never learns that an observer rebooted, changed address, or fell off the network, and will keep emitting to nobody; the loss is invisible on both sides.
- **Out-of-order notifications regress a reading.** Two notifications sent close together can arrive reversed over UDP; a client that ignores the Observe sequence number will display the older sample as current.
- **NON telemetry disappears silently.** There is no queue and no retained value, so a sample emitted while the collector is restarting is gone, and nothing in the protocol reports it.
- **Blocking inside a resource handler stalls the protocol machinery.** Retransmission timers and pending notifications only advance inside `coap_io_process`, so a long sensor read inside the handler delays unrelated confirmable exchanges into their retransmits.
- **DTLS record buffers compete with the rest of the heap.** The mbedTLS memory pressure that affects MQTT over TLS applies identically here; sizing must be checked against free heap on the target, not on a desktop build.
- **Assuming CON means exactly-once.** Confirmable delivery is at-least-once: an ACK lost on the return path causes a retransmission, and only the Message ID deduplication window prevents a repeated request from being executed twice — a window, not a permanent record.
