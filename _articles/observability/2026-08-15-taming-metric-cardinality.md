**Gist.** A time-series database charges per *series*, not per metric, so adding one unbounded label to an existing counter multiplies memory and index cost by the number of distinct values that label takes. The remedy is a two-stage defence: `metric_relabel_configs` rewrites or deletes the offending label between scrape and storage, and per-job scrape limits reject a target whose output exceeds a declared budget. The cost of the second stage is asymmetric — a tripped `sample_limit` discards *every* sample from that scrape, so the protection is bought by going blind to the misbehaving instance.

## What a series is, and why labels multiply

Prometheus does not store metrics. It stores **time series**, and a series is identified by the full set of a metric name plus every label key/value pair attached to it. `http_requests_total{method="GET", status="200", handler="/api"}` and `http_requests_total{method="GET", status="200", handler="/login"}` are two distinct series: two separate on-disk chunk streams, two separate entries in the in-memory index.

The count of series generated by a metric is bounded above by the **Cartesian product** of its label domains. A metric carrying 5 methods, 20 status codes and 40 handlers has at most 5 × 20 × 40 = 4,000 series. Every factor in that product is finite and enumerable, so the total is predictable. Introducing `user_id` with 500,000 distinct values raises the upper bound to two billion. The realised count is smaller — only combinations that appear in traffic are materialised — but "the subset traffic happens to produce" is still measured in millions, and no configuration bounds it.

The cost lands in the **head block**, the in-memory window holding the most recent, still-being-written samples. Each *active* series holds an index entry plus an open chunk that appends are written into. Memory therefore scales with **the number of series being ingested, not with the number of samples per series**: a series receiving one sample every 15 seconds and a series receiving one sample per day cost the same resident structures while both are active. This is the asymmetry Robust Perception's "Cardinality is key" names — the failure is not gradual degradation but resident-set growth until the process is OOM-killed, and the killed process must replay the write-ahead log on restart, so the failure repeats.

The operational rule follows directly from the product bound: **a label value must be drawn from a small set that could be written down in advance.** User identifiers, raw URL paths with embedded IDs, email addresses, and full Kubernetes pod names carrying a random suffix all fail that test. A pod name is a particularly quiet offender because it is bounded at any instant but unbounded over time — every deployment mints a new set of values, and the old series remain resident until they fall out of the head block.

## Locating the offender

The TSDB status endpoint reports the head-block breakdown directly, so diagnosis does not require guessing:

```bash
curl -s http://localhost:9090/api/v1/status/tsdb | jq '.data'
```

Two fields carry the diagnosis. `seriesCountByMetricName` ranks metric names by series owned, which identifies *which* metric grew. `labelValueCountByLabelName` ranks label names by distinct values observed, which identifies *why* — a label appearing here with a value count in the thousands is the multiplier. The same breakdown is rendered in the web interface under **Status → TSDB Stats**.

PromQL confirms the reading and quantifies it:

```promql
# Top 10 metrics by number of series
topk(10, count by (__name__) ({__name__=~".+"}))

# For a suspect metric, the number of distinct values of one label
count(count by (user_id) (http_requests_total))
```

The inner `count by (user_id)` collapses the metric into one entry per distinct `user_id`; the outer `count` reports how many entries that produced. A result of 500,000 is the multiplier stated numerically.

## Stage one: relabeling

`metric_relabel_configs` runs **after a scrape completes and before samples are appended to storage**. It is distinct from `relabel_configs`, which acts on *target* labels during service discovery, before the scrape is issued. Only the former can act on a label emitted by the application itself, because only the former sees the scraped sample.

```yaml
scrape_configs:
  - job_name: app
    static_configs:
      - targets: ["app:8080"]
    metric_relabel_configs:
      # 1. Delete unbounded labels entirely
      - regex: '(user_id|trace_id|session_id)'
        action: labeldrop

      # 2. Collapse a high-cardinality path onto a template
      - source_labels: [path]
        regex: '/api/users/[0-9]+'
        target_label: path
        replacement: '/api/users/:id'

      # 3. Drop an entire metric family that is never queried
      - source_labels: [__name__]
        regex: 'go_gc_duration_seconds.*'
        action: drop
```

The three actions differ in what survives. `labeldrop` (#1) matches against **label names**, not values, and removes the matching labels from every sample in the scrape; the remaining labels of formerly distinct series may now collide, leaving several samples with an identical label set in one scrape, of which only one value is retained. Rewriting (#2) keeps a bounded projection of the label — the path shape remains queryable while the identifier is discarded. `drop` (#3) removes whole samples, so the series family disappears rather than being collapsed. Where a target is chronically noisy, a `keep`/`labelkeep` allow-list bounds the result by construction, whereas a list of `drop` rules only bounds what has already been observed.

### Implementation sketch (Scala)

The relabeling stage is a fold of ordered rules over a label set, where each rule may rewrite the set or reject the sample outright. The load-bearing property is that **rules are applied in declaration order and each sees the output of the previous one**, so a rewrite can feed a later match.

```scala
type Labels = Map[String, String]

enum Action:
  case Drop, Keep, LabelDrop, Replace

final case class Rule(
    action: Action,
    regex: scala.util.matching.Regex,
    sourceLabels: List[String] = Nil,
    targetLabel: String = "",
    replacement: String = "",
    separator: String = ";"
)

/** Returns None when the sample is dropped, Some(labels) otherwise. */
def apply(rules: List[Rule], in: Labels): Option[Labels] =
  rules.foldLeft(Option(in)):
    case (None, _)          => None // a dropped sample stays dropped
    case (Some(ls), rule)   =>
      val joined = rule.sourceLabels.map(ls.getOrElse(_, "")).mkString(rule.separator)
      val hit    = rule.regex.matches(joined)
      rule.action match
        case Action.Drop      => if hit then None else Some(ls)
        case Action.Keep      => if hit then Some(ls) else None
        case Action.LabelDrop =>
          // matches label NAMES, so distinct series may collapse into one
          Some(ls.filterNot((name, _) => rule.regex.matches(name)))
        case Action.Replace   =>
          if hit then Some(ls.updated(rule.targetLabel, rule.replacement)) else Some(ls)
```

The collapse in the `LabelDrop` branch is the observable consequence worth noting: two samples that differed only in `user_id` reduce to the same label set within one scrape.

## Stage two: scrape limits

Limits are the guardrail for the label that was not anticipated. Configured per scrape job, they convert silent head-block growth into a visible target failure.

| Field | Enforces | Effect on breach |
|-------|----------|------------------|
| `sample_limit` | max samples accepted per scrape | whole scrape rejected, target marked down |
| `label_limit` | max labels per series | scrape rejected |
| `label_name_length_limit` | max label-name length | scrape rejected |
| `label_value_length_limit` | max label-value length | scrape rejected |
| `target_limit` | max targets per job after relabeling | scrape job fails |

```yaml
scrape_configs:
  - job_name: app
    sample_limit: 50000        # refuse a scrape carrying more than 50k samples
    label_limit: 30
    label_value_length_limit: 512
    static_configs:
      - targets: ["app:8080"]
```

The trade-off is explicit in the "effect on breach" column: **`sample_limit` protects the server by sacrificing the target.** When it trips, no samples from that scrape are stored, which removes visibility into the instance whose behaviour caused the trip. It is a backstop against unbounded growth, not a cardinality strategy. The durable fix is upstream — high-cardinality identifiers belong on exemplars, traces or logs, where storage is keyed by event rather than by label combination.

The field names and behaviour described here follow the Prometheus 3.13 configuration reference.

## Pitfalls

- **`relabel_configs` is used where `metric_relabel_configs` is required.** The rule never matches an application-emitted label, because service-discovery relabeling runs before the scrape and sees only target metadata.
- **`labeldrop` regexes are written against label values.** The action matches label *names*; a regex describing values matches nothing and the cardinality is unchanged.
- **Dropping a label collapses distinct series onto one label set.** Samples that differed only in the dropped label become duplicates within a single scrape rather than summing, so the surviving value is one instance's, not the total.
- **`sample_limit` blinds the operator to the offender.** A breach rejects the entire scrape and marks the target down, so the instance producing the runaway labels is the one that stops reporting.
- **Pod names look bounded and are not.** Cardinality is finite at any instant but grows with every deployment, so the head block accumulates series that no longer receive samples.
- **Limits are set from current series counts on a job already over budget.** A limit derived from an inflated baseline permits the inflation it was meant to catch.
- **A `drop` list is maintained instead of a `keep` list.** Each new unbounded label requires a new rule discovered after the fact, whereas an allow-list bounds the label set in advance.
