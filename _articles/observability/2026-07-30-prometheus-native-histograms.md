If you have ever tuned a Prometheus histogram, you know the ritual: guess a list of bucket boundaries, deploy, discover your p99 lands between two buckets, add more buckets, and pay for every one of them forever. Native histograms — one of the marquee features that shipped with [Prometheus 3.0](/articles/observability/2026-07-25-prometheus-3-whats-new) and reached stable in v3.8.0 — delete that ritual. This is a focused look at what they are and how to run them.

## The problem with explicit buckets

A classic histogram is not one series. `http_request_duration_seconds` with 12 `le` boundaries becomes 12 `_bucket` series (plus `_count` and `_sum`), one per boundary, each carrying every other label you attach. Cross that with a handful of routes, methods, and status codes and a single histogram quietly turns into thousands of series.

That cost buys surprisingly little accuracy. The boundaries are fixed at instrumentation time, so you have to predict the shape of a distribution you have not measured yet. `histogram_quantile` linearly interpolates *within* whichever bucket the quantile falls into, so a p99 that lands inside a bucket spanning 1s–2.5s is an educated guess. When latency shifts — a new dependency, a bad deploy — the interesting values pile into the top bucket where you have the least resolution, exactly when you need the most.

So you face a permanent trade-off: more buckets for accuracy, or fewer buckets for cost. Native histograms remove the trade-off.

## How native histograms work

A native histogram is a **single time series** that carries a *sparse* set of exponential buckets. Bucket boundaries are not chosen by you; they are generated by a `schema` integer. For a standard schema *n*, positive bucket boundaries are:

```
(2 ** (2 ** -n)) ** i        # i is the bucket index
```

Schema *n* has exactly half the resolution of schema *n*+1, so a higher schema means narrower buckets and finer quantiles. Standard exponential schemas run from **-4 to 8**; schema **-53** is reserved for custom (explicit) boundaries stored in the native format. The resolution is *relative*: buckets are narrow where your data is dense and automatically wider in the tail, so a slow request never falls off a cliff of resolution.

Crucially the representation is **sparse** — only populated buckets are stored. An endpoint whose latency clusters between 20ms and 300ms stores a dozen buckets, not the full schema's range. And it is *one* series regardless of resolution, so bumping accuracy no longer multiplies your cardinality.

You pick resolution by a **bucket growth factor** rather than the raw schema. Some reference points:

| Factor | Schema | Meaning |
|--------|--------|---------|
| 1.1    | 3      | each power of two split into 8 buckets |
| 1.05   | 4      | ~16 buckets per power of two |
| 1.01   | 7      | ~128 buckets per power of two |

Factor **1.1 (schema 3)** is the documented sweet spot: roughly 10% relative error per bucket, a small fixed number of buckets, and one series. Compare that to a classic histogram needing dozens of `le` series to approach the same tail accuracy.

## Instrumenting one in Go

With `client_golang`, you turn a classic histogram into a native one by setting `NativeHistogramBucketFactor`. You can omit `Buckets` entirely — the exponential scheme replaces explicit boundaries:

```go
histogram := prometheus.NewHistogramVec(
    prometheus.HistogramOpts{
        Name: "http_request_duration_seconds",
        Help: "Request latency.",
        // Enables native-histogram mode. 1.1 -> schema 3.
        NativeHistogramBucketFactor: 1.1,
        // Cap live buckets; on overflow the SDK widens the zero
        // bucket or halves resolution rather than exploding.
        NativeHistogramMaxBucketNumber:  160,
        NativeHistogramMinResetDuration: time.Hour,
    },
    []string{"route", "method", "code"},
)
```

`NativeHistogramMaxBucketNumber` is your safety valve: if a misbehaving distribution tries to populate too many buckets, the client library first waits out `NativeHistogramMinResetDuration`, then either widens the zero bucket or reduces the schema — bounding memory without you intervening. Values at or below `NativeHistogramZeroThreshold` (default 2^-128) collapse into a single zero bucket.

Native histograms are carried in Prometheus's **protobuf exposition format**, so the client library negotiates protobuf on scrape automatically. You do not change your `/metrics` handler.

## Enabling ingestion

Native histograms were experimental from v3.0 through v3.7, gated behind `--enable-feature=native-histograms`. As of **v3.8.0 (Nov 2025)** they are a stable, opt-in feature controlled per scrape config (latest release as of this writing is v3.13.0):

```yaml
# prometheus.yml
scrape_configs:
  - job_name: my-app
    scrape_native_histograms: true   # stable, v3.8+
    static_configs:
      - targets: ["app:8080"]
```

The old `--enable-feature=native-histograms` flag still works in v3.8 (it just flips the default of `scrape_native_histograms` to true) and becomes a no-op in v3.9, so migrate to the config setting.

## Querying them in PromQL

This is where the ergonomics pay off. Because the buckets live inside one series, you do **not** aggregate by `le` — there is no `le` label. p99 latency is just:

```promql
histogram_quantile(
  0.99,
  sum by (route) (rate(http_request_duration_seconds[5m]))
)
```

Note that `rate()` and `sum()` operate directly on the native-histogram series and return a native histogram; `histogram_quantile` consumes it. Companion functions read the same series:

```promql
# request rate straight from the histogram (no separate _count series)
histogram_count(rate(http_request_duration_seconds[5m]))

# mean latency = sum / count
histogram_sum(rate(http_request_duration_seconds[5m]))
  / histogram_count(rate(http_request_duration_seconds[5m]))

# fraction of requests served under 300ms (an SLI, directly)
histogram_fraction(0, 0.3, rate(http_request_duration_seconds[5m]))
```

`histogram_fraction(lower, upper, v)` is the one you could never express cleanly with classic buckets unless a boundary happened to sit exactly at your SLO threshold. Now the threshold is arbitrary.

## OpenTelemetry interop

If you emit OTel, this maps cleanly. An OpenTelemetry **exponential histogram** and a Prometheus native histogram are the same idea: OTel's `scale` equals Prometheus's `schema`, the zero bucket matches OTel's zero count, and bucket indices differ only by a one-off offset. Prometheus's native OTLP receiver converts OTel exponential histograms into native histograms on ingest, so an OTel-instrumented service and a `client_golang` one land in the same high-resolution shape — no explicit buckets on either side.

## The trade-off, honestly

Native histograms are not free of caveats. Long-term-storage backends and query tooling need explicit support (Mimir, Thanos, Cortex, and managed services have added it, but check yours). Recording rules and dashboards written against `_bucket`/`le` need rewriting. And because a series can silently change resolution under load, alerting on exact bucket boundaries is out. But for the common case — latency and size distributions — you trade a fixed guess and per-bucket billing for one self-scaling series with better tails.

**Try next:** pick your busiest classic histogram, add `NativeHistogramBucketFactor: 1.1` (keep the old `Buckets` during migration so both coexist), enable `scrape_native_histograms`, and diff `histogram_quantile(0.99, ...)` from each in Grafana — then count the series you delete when you drop the explicit buckets.
