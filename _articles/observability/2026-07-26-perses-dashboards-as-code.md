**Gist.** Grafana stores a dashboard as a user-interface-first JSON document, so version control sees an export artefact rather than a source, and review of a change reduces to reading a machine-serialised diff. Perses inverts the direction: **the dashboard is a typed resource with a declared schema, and the authoring form is a program — written in Go or in CUE — that a compiler turns into that resource**. The cost is a build step between edit and render, a plugin catalogue and data-source coverage far narrower than Grafana's, no alerting engine at all, and a schema that is still pre-1.0 and therefore carries no compatibility guarantee between minor releases.

## Provenance and governance

Perses originated at Amadeus, where Augustin Husson — also a contributor to Prometheus — led the work, and it was unveiled publicly at PromCon. The reported motivation was the scale of a Grafana estate large enough that dashboard management had become unmanageable by hand; the failure mode described is structural rather than operational: because the stored form of a Grafana dashboard is a UI-exported JSON blob, "dashboard as code" in practice meant clicking through the editor, exporting, and committing the export.

The project was accepted into the **CNCF Sandbox in 2024** and is governed under the Cloud Native Computing Foundation rather than by a single vendor. There is no 1.0 release, so the schema carries no stability guarantee across minor versions. Red Hat ships Perses as part of its OpenShift observability tooling.

## The typed dashboard resource

A Perses dashboard is a structured resource: `kind: Dashboard`, carrying `metadata` and a `spec` composed of `panels`, `layouts`, `variables` and `datasources`. The consequence of having a declared schema rather than an opaque export is threefold — **the document can be validated statically, it diffs along semantic boundaries in a pull request, and it can be generated by a program instead of hand-edited**.

Generation is the feature the project is organised around: **Dashboards-as-Code (DAC)**. The author writes a program that constructs the dashboard object, and the `percli` command-line interface compiles that program down to the resource the server stores. The construction language supplies loops, functions and shared building blocks for panel groups and variables directly, in place of the macro layer that Grafana's unofficial `grafonnet`/Jsonnet ecosystem provides.

A trimmed CUE example, adapted from the official getting-started guide:

```cue
package mydac

import (
	dashboardBuilder "github.com/perses/perses/cue/dac-utils/dashboard"
	panelGroupsBuilder "github.com/perses/perses/cue/dac-utils/panelgroups"
	panelBuilder "github.com/perses/plugins/prometheus/sdk/cue/panel"
	timeseriesChart "github.com/perses/plugins/timeserieschart/schemas:model"
	promQuery "github.com/perses/plugins/prometheus/schemas/prometheus-time-series-query:model"
	promDs "github.com/perses/plugins/prometheus/schemas/datasource:model"
)

dashboardBuilder & {
	#name:    "ContainersMonitoring"
	#project: "MyProject"

	#panelGroups: panelGroupsBuilder & {
		#input: [
			{
				#title: "Resource usage"
				#cols:  3
				#panels: [
					panelBuilder & {
						spec: {
							display: name: "Container memory"
							plugin: timeseriesChart
							queries: [{
								kind: "TimeSeriesQuery"
								spec: plugin: promQuery & {
									spec: query: "max by (container) (container_memory_rss{namespace=\"$namespace\"})"
								}
							}]
						}
					},
				]
			},
		]
	}.panelGroups

	#datasources: promDemo: {
		default: true
		plugin: promDs & {spec: close({directUrl: "https://demo.prometheus.com"})}
	}
}
```

The `&` operator is CUE unification: `panelBuilder & { ... }` constrains the builder's schema with the supplied fields, and any field that contradicts the schema fails at evaluation rather than at render. `close({...})` marks the struct as admitting no further fields, so a misspelled key inside the datasource specification is an error instead of silently ignored extra data.

The build and apply sequence:

```bash
# one-time setup
cue mod init mydac
percli dac setup            # or: percli dac setup --language go
cue mod tidy

# compile the DAC program to a Perses resource
percli dac build -f dashboard.cue -o dashboard.yaml

# apply it to a running Perses instance
percli apply -f dashboard.yaml
```

The Go software development kit (SDK) expresses the same construction with fluent builders — `dashboard.New(...)`, `dashboard.AddPanelGroup(...)`, `panel.AddQuery(query.PromQL(...))` — which keeps dashboard definitions inside a language the team already compiles, tests and lints.

## Perses compared with Grafana

| | Perses | Grafana |
|---|---|---|
| Governance | CNCF Sandbox, Linux Foundation, multi-vendor | Grafana Labs, single-vendor |
| License | Apache 2.0 | AGPLv3 (since the 2021 relicense) |
| Dashboard model | Typed, versioned schema; API resource | UI-exported JSON blob |
| Dashboards-as-code | Native Go/CUE SDKs + `percli` | Unofficial community tooling (Grafonnet, Jsonnet) |
| Kubernetes story | Native CRDs (`PersesDashboard`, `PersesDatasource`) via the Perses Operator | Community Grafana Operator, less native |
| Embedding | Front-end components published as npm packages, usable outside the app | Panels embed mainly via iframe/snapshot |
| Alerting | None — visualization only | Built-in alerting engine |
| Data sources | Plugin-based, centred on Prometheus with further plugins available | Very broad, large plugin catalogue |

Grafana retains the advantage on breadth of data sources, on alerting, and on ecosystem maturity. **Perses is the better fit only where the dashboard format itself is the object of interest** — a format that can be generated, validated in continuous integration, and reconciled by Argo CD or Flux under the same mechanism as every other cluster resource.

## Kubernetes-native deployment

Beyond the command-line interface, the [Perses Operator](https://github.com/perses/perses-operator) exposes dashboards as first-class Kubernetes objects:

```yaml
apiVersion: perses.dev/v1alpha1
kind: PersesDashboard
metadata:
  name: containers-monitoring
  namespace: monitoring
spec:
  config:
    kind: Dashboard
    metadata:
      name: containers-monitoring
      project: MyProject
    spec:
      display: {name: "Containers Monitoring"}
```

The operator reconciles the custom resource against a running Perses server. **The reconciliation loop makes the Perses server's dashboard set a function of the manifests in the cluster, not of what an operator last clicked**, which places the dashboard in the same namespace, the same repository and the same pull request as the workload it observes.

## Local operation

```bash
docker run -d -p 8080:8080 persesdev/perses:latest
# or, from source:
git clone https://github.com/perses/perses && cd perses
make build
./bin/perses --config ./config.yaml
```

A Prometheus data source is registered through the user interface or through `percli apply -f datasource.yaml`, after which any dashboard resource produced by the DAC SDK can be applied.

## Position relative to Prometheus

Perses is neither a Prometheus fork nor a time-series database: it holds no storage engine and no alerting of its own. It is a visualization layer with native Prometheus support, listed in Prometheus's own documentation as a visualization option alongside Grafana. Because the dashboard is compiled against a declared schema, **a structurally invalid dashboard fails at `percli dac build` — inside continuous integration — rather than surfacing as a broken panel during an incident**. The check is on the shape of the resource, not on the contents of any particular server, so a well-formed query naming a series that does not exist still compiles.

## Pitfalls

- **Pre-1.0 schema.** No 1.0 release exists, so a `spec` field accepted by one minor release carries no compatibility guarantee in the next; a DAC program pinned to an older SDK can fail to build after a minor upgrade.
- **No alerting.** Perses is visualization only. A migration that removes Grafana also removes its alerting engine, and the rules must be relocated — to Prometheus Alertmanager or elsewhere — before the dashboards move.
- **Data-source coverage is the binding constraint.** The plugin catalogue is far narrower than Grafana's. A dashboard sourced from anything outside it has no port.
- **A compiling dashboard is not a populated dashboard.** Schema validation checks the resource, not the data; a metric name that no target exposes builds cleanly and renders empty.
- **`close()` is not the default.** A datasource or panel struct left open accepts unrecognised fields, so a typo produces a dashboard missing the intended setting rather than a build error.
- **The build step is a new failure surface.** `percli dac build` sits between the edit and the rendered panel; a `cue mod tidy` that resolves a plugin module to a different version can change generated output with no edit to the dashboard program itself.
- **Operator scope.** The `PersesDashboard` custom resource is reconciled against a running Perses server; if that server is unreachable the manifest applies successfully to Kubernetes while the dashboard never appears.
